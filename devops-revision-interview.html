Week 1

What DevOps actually is

Concept

DevOps is not a job title you paste on LinkedIn. It is a way of shipping software: developers and operations share one path so a change is built, checked, and run the same way every time. In IT support you already debug a broken PC. In DevOps you debug the path that creates and runs the system: Git history, a pipeline, an image, a server, a metric.

A useful definition you can say in an interview: DevOps is making build, test, release, and operations repeatable and automatic so changes stay small and failures show up in a pipeline or a dashboard instead of only in a user ticket.

CI (continuous integration) is the automatic check on every change. CD (continuous delivery/deployment) is releasing that checked artifact automatically or with one click. You have built CI. You have not built full CD. Say that clearly.

you edit files

   → CI runner (rented Ubuntu) builds + tests
   → optional: image goes to a registry (GHCR)
   → a machine runs it (laptop, then EC2)
   → metrics/logs tell you if it is alive

Support ticket:  user says it is broken → you look
DevOps path:    pipeline or dashboard says it is broken → you look earlier

Week 1

Permissions (rwx and chmod)

Concept

Every file has three groups of rights: owner, group, others. Each group can have read (r), write (w), execute (x). Numbers are the same idea: 4 = read, 2 = write, 1 = execute. Add them: 4+2+1 = 7 means rwx, 4+2 = 6 means rw, 4 = r only.

Directories need execute to enter them. A script needs execute to run with ./hello.sh.

SSH is strict: if your private key is readable by others, ssh refuses it. That is why chmod 400 on a .pem. Permissions are not enough for Git: a secret with mode 644 in a public repo is still a leak — do not commit secrets.

Architecture

letter form          number     meaning
rwx------            700        only owner, full
rw-------            600        secrets: only you read/write
r--------            400        private keys (.pem)
rw-r--r--            644        normal files
rwxr-xr-x            755        scripts and directories
rwxrwxrwx            777        everyone — almost never

chmod 400 ~/.ssh/devops-lab-ec2.pem
ls -l  →  -r--------  (the leading - is “regular file”)
         d at the start would mean directory

What you actually built

You set chmod 400 on devops-lab-ec2.pem so SSH would accept the key. You used chmod +x on bash scripts.

Week 2

Git, remotes, SHA

Concept

Git stores snapshots of files. Each snapshot is a commit: a message, a parent, and a SHA (a fingerprint). A branch is a movable name pointing at a commit. main is the line you treat as the default.

A remote is another copy of the repo. origin in your lab is GitHub. You also added gitlab as a second remote — two websites, two lockboxes, same commits when you push both.

git add stages (choose what goes into the next snapshot). git commit writes the snapshot locally. git push sends commits to the remote. git pull brings remote commits home.

If GitHub moved and you did not: rejected, fetch first. You pull (merge), then push. You do not --force on main — that rewrites history other people (or you on another machine) may have.

You used the commit SHA as a Docker image tag so the image and the git snapshot are the same change.

gitlab   = gitlab.com/engr.fs100/devops-lab

never commit: .pem, terraform.tfstate, .terraform/, secret.txt

Bash scripts and exit codes

Concept

Bash is the shell. A script is a text file of commands. Line 1 #!/bin/bash (shebang) tells Linux to run this file with bash. chmod +x plus ./hello.sh executes it.

$? is the exit code of the last command: 0 means success, anything else is failure. CI and scripts use that. set -e stops the script at the first failing command so you do not continue on a broken state.

GitHub Actions run: | blocks are bash on the runner. Your backup script with tar and a date in the filename is the same idea as a tiny operations job.

Architecture

#!/bin/bash          shebang: run with bash
set -e               stop on first error
echo "hello $USER"   $USER is a variable
exit 0               optional explicit success

chmod +x hello.sh
./hello.sh           run THIS file in THIS folder
echo $?              print last exit code

Week 2

Networking: IP, DNS, ports, HTTP

Concept

An IP address is the machine. DNS maps a name to an IP. A port is a numbered door on that machine. HTTP is a request/response on a port (80 or 443). Status codes: 200 OK, 404 not found, 500 the server program crashed, 403 forbidden.

Important ports: 22 SSH, 80 HTTP, 443 HTTPS, 8080 often “HTTP but not 80” (your Docker publish). Ping uses ICMP — it is not HTTP. Ping can work while the website is down.

In AWS a security group is a firewall in front of the instance: it allows or denies ports from CIDR ranges. 0.0.0.0/0 means every IPv4 address. YOUR_IP/32 means only you.

Architecture

80   HTTP         host nginx
443  HTTPS        GitHub, GitLab
8080 Docker web   -p 8080:80

  1. process running?   systemctl / docker ps
  2. port listening?    ss -tuln
  3. HTTP answer?       curl -I
  4. firewall?          security group, local firewall
  5. logs

What you actually built

Week 3

Docker: image, container, registry

Concept

An image is a packaged filesystem plus a default start command — the recipe. A container is a running (or stopped) instance of that image — one cake from the recipe. A registry is a warehouse of images (Docker Hub, GHCR).

A tag is a sticker on an image: hello-site:ci is a local nickname you chose. It is not a special Docker mode. nginx:alpine means the nginx image, alpine variant. Your CI also tags with the git SHA for GHCR.

-p 8080:80 means: host port 8080 forwards to container port 80. curl localhost:8080 on the host. Inside the container nginx still thinks it is on 80.

docker run -d starts in the background. It does not wait until nginx is ready to answer HTTP — that is why CI curl needed a retry loop. Exit code 56 was “connection reset / not ready yet.”

A container vs a VM: a VM emulates a whole machine (guest kernel). A container shares the host kernel and isolates a process with its own filesystem. Lighter, faster to start, not a full OS.

Architecture

Dockerfile  →  docker build -t NAME:TAG  →  image (recipe)
docker run  →  container (running copy)
docker push →  registry (GHCR / Docker Hub)

-p 8080:80     host 8080  →  container 80
--name ci-web  a name so you can logs/stop without copying IDs
-d             detached (background)
--rm           delete container when it stops (image stays)

hello-site:ci     local name on the CI runner / your laptop
ghcr.io/fahadsafdar-crypto/devops-lab:<sha>   warehouse name

What you actually built

Say this:

Two. First, curl failed with 56 because I treated docker run -d as “HTTP is ready.” I added a retry loop and fail the job if it never answers. Second, GHCR returned 403 because GITHUB_TOKEN was not allowed to create a package named hello-site. I set packages: write and pushed ghcr.io/fahadsafdar-crypto/devops-lab:SHA to match the repository.

Say this:

I thought the variable description field was the CIDR. It is only help text. ssh_cidr must be passed with -var, using my public IP /32. I also learned destroy does not delete the .tf files, and the SSM parameter name is not the AMI id.

Do not memorise AMI ids, provider plugin versions, or marketplace action SHAs. Memorise structure. Cover the page and write on paper.

A. GitHub Actions

name: CI
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t hello-site:ci ./docker/hello-site

B. GitLab CI

stages:
  - build
build-image:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  variables:
    DOCKER_TLS_CERTDIR: ""
  script:
    - docker build -t hello-site:ci ./docker/hello-site
